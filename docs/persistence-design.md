# I01 local persistence design

This first slice stores synthetic vacancy metadata, not private CVs or raw source content. The CLI remains database-free. The adapter uses ElectroDB to construct entity keys and the AWS SDK v3 Document Client for transactional operations. A trusted caller supplies the tenant identity; partitioning by tenant is not authentication or authorization. Future API and workers must independently enforce ownership.

## Access patterns and constraints

- Create a canonical vacancy with a tenant-scoped source/external-ID claim; use a transaction and conditional writes to prevent concurrent duplicate claims. A repeated claim is not, by itself, evidence that content is unchanged.
- Read a vacancy and its version by tenant and ID; resolve a source/external ID within a tenant. Attach and list multiple source references without a scan. Read source claims and canonical records consistently when needed.
- List a tenant's recent vacancies using a paginated secondary index. Index reads are eventually consistent; pagination is not a snapshot. Cursors are tenant-bound and HMAC-signed with a caller-supplied secret of at least 32 bytes; the secret must remain private and stable across requests and processes or existing cursors become invalid.
- Replace a vacancy with an expected version and atomically retain its version snapshot. A conflict is not a successful update; retries require explicit handling. No normal path requires an unbounded scan.

The initial table uses tenant-scoped partition keys with separate vacancy, version and source-claim entities, plus a tenant/recent-time index. These are implementation choices for these access patterns, not a general requirement to place every future entity in one table. Source names and original external IDs are retained as private runtime metadata; a hash of each source/external-ID pair is used for the deduplication key and is not anonymization. An optional human-openable HTTPS source URL may be retained without userinfo, query or fragment; callers must ensure its path contains no secrets. Links requiring excluded components need a manual fallback rather than silent URL rewriting. Storing a URL does not authorize fetching it. Do not put credentials, raw CVs or message bodies in metadata. Retention and deletion rules remain to be designed before production.

The initial filesystem object adapter is POSIX-only (it requires `getuid` and `O_NOFOLLOW`), requires a pre-created, private canonical root and trusted ancestor directories that cannot be modified or replaced by untrusted users, and caps each object at 1 MiB. Windows support and larger-artifact/S3 storage are future work. It checks canonical paths and rejects symlinks, but path-based checks and later operations are not atomic: it does not protect against an attacker who can change an ancestor or a malicious process under the same OS identity. It stores opaque tenant/object IDs, size and SHA-256 integrity metadata. It is not a substitute for OS isolation or API authorization. Object writes and database transactions are not atomic together; consumers must design retry-safe references, reconciliation and orphan cleanup before integrating the stores. No exactly-once notification guarantee follows from this design. Future AWS use needs separate private S3 buckets, least-privilege IAM, encryption, retention and authorized cloud verification.

## Local isolation

`infrastructure/docker/compose.yml` defines a pinned DynamoDB Local image, bound to loopback and configured in-memory. Local tests must require an explicit loopback endpoint and dummy credentials; no SDK credential-chain or production endpoint fallback is allowed. Tests use isolated tables. Emulator success does not validate AWS IAM, encryption, TTL, distributed failures or deployment behavior.

## Running local integration tests

Start the in-memory service with `docker compose -f infrastructure/docker/compose.yml -p roleriver-i01 up -d`. Then run `ROLERIVER_DYNAMODB_TEST=1 ROLERIVER_DYNAMODB_TEST_URL=http://127.0.0.1:18000 mise exec -- pnpm test:integration`. The explicit test command fails if the opt-in or endpoint is missing; the endpoint must be loopback-only and tests use isolated tables and dummy credentials. Default `mise run check` runs without the emulator or AWS credentials. Stop the dedicated container afterwards with `docker compose -f infrastructure/docker/compose.yml -p roleriver-i01 down`; its in-memory data is ephemeral. The image is pinned by version and digest. The provided local client accepts only an explicit loopback endpoint and dummy credentials; production AWS client configuration is future work. CI starts the same local service for integration tests; its hosted run is not yet verified.

A duplicate create is accepted only for matching existing metadata; changed metadata is a conflict rather than a silently ignored update. If a write's outcome is ambiguous, a caller must reconcile against stored records before retrying: replays of the same create/source attachment can report duplicate, while replaying a committed replacement with its old version reports a conflict. A conflict alone does not say whether the prior attempt or another writer won. Full cross-store recovery remains future work, not an implemented guarantee. Provenance records missing a recoverable external ID fail closed and require an explicit migration before they can be read. Source reference digests are sensitive derived data and are not anonymization.

## Deferred access patterns

The current table and index design covers the vacancy slice only. Before adding other records, define and test queries for a candidate's assessments by vacancy and profile version, confirmed deadlines by tenant and time window, and per-source synchronization checkpoints and recovery. Their keys, indexes, retention and concurrency rules remain undecided; none should depend on unbounded scans. Do not assume the existing table layout is the final schema for every domain record.
