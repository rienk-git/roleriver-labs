# I02 recovery and visibility proposal

Status: approved by the owner for implementation; Gmail activation remains subject to integrated testing and security review. This design aims to keep local operation simple while making failure and retention behavior explicit. It does not specify a cloud implementation.

## Retention

The owner chose to delete Gmail text, including evidence quotations, when it is no longer needed for an active role. A message may be needed for processing before a role exists, or by more than one role. Track explicit processing and role/evidence holds; release each hold when that use ends. Only content with no remaining holds becomes eligible for deletion. A Gmail selection change alone does not establish that content is no longer needed. On Gmail disconnect, delete locally retained Gmail-derived text and quotations even if a role is still active; stop ingestion, invalidate holds and retry deletion until completed. Never send Gmail-derived text to external AI without the separate policy and consent review.

## Local object lifecycle

Legacy Gmail and current manual-import objects use tenant-scoped content digests as IDs, so identical content can be shared. Do not delete these legacy objects based solely on Gmail references, age or a lease timeout. Reconcile all producers and references before migration or deletion; legacy temporary filenames can also be valid object IDs.

For new Gmail writes, propose an opaque, unique and never-reused object ID per content version. Before writing, create a durable intent under the current connection fence. Write and verify the object, then atomically publish the ledger reference and resolve the intent in DynamoDB under the same fence. When the last hold is released, atomically mark the reference unavailable and enqueue deletion; delete idempotently, then record completion. Fail closed if a referenced object is missing or fails its integrity check. Retry interrupted writes and deletions without exposing partial results.

A tenant-wide, cross-process local barrier must encompass every participating write, publication and cleanup operation. Recovery may delete an abandoned object only after acquiring the barrier and establishing that the writer has actually stopped; a fence pre-check, timeout or grace period alone does not prevent a delayed write from recreating it. The barrier must cover all relevant processes and drain in-flight writes before it is released. Its exact implementation and crash behavior need independent security review. A local barrier is not a distributed S3 fence; a separate cloud protocol and review are required before cloud activation.

## Sync visibility

The current ledger overwrites records in place, and both full and incremental attempts can leave partial mutations after interruption. Propose a durable per-source attempt marker created before the first mutation. Publish successful attempt completion and its checkpoint together in one fenced transaction. Readers must fail closed while an attempt is incomplete; the previous view cannot be reconstructed from overwritten records. Multi-page reads must prevent concurrent mutations or validate a monotonic epoch after buffering all pages and before returning results. A different immutable-generation design is possible if a continuously available previous view becomes a requirement.

Claim each configuration version against a canonical fingerprint of its full query and label selection before any mutation. Store claims durably so reuse with a different selection fails even after another version or an interrupted initial sync. A fenced claim adapter is wired into the polling contract and integration tests, but not a production composition root. The coordinator takes one immutable configuration snapshot for the claim and the entire poll. Existing checkpoints without prior claims fail closed; a newly created claim does not prove what older records used, so migration remains necessary.

## Required evidence before activation

Test crashes and ambiguous outcomes around intent creation, object writes, publication, hold release and deletion; stale writers; multiple references and tenants; legacy shared content; restart and retry; incomplete full and incremental syncs; concurrent paginated reads; and configuration-version reuse. Use synthetic data and local infrastructure, with independent architecture, QA and security review. The existing inactive ledger does not yet provide these guarantees.

Sync attempts and configuration claims are integrated into the polling contract, with tests for partial synchronization and fail-closed legacy checkpoints. A local composition connects the ledger, object lifecycle, barrier and hold release in synthetic integration tests. It requires empty, private and quiescent roots on first initialization and a new dedicated local table; existing bindings must match. After interrupted initialization, stop all writers and audit the roots and table offline before any repair; do not automatically remove or recreate markers. Legacy digest-backed content still needs a migration. The lifecycle's generic transaction actions rely on trusted callers for ownership, hold and disconnect invariants, and the local composition has not been activated or reviewed as a complete production flow. Do not activate Gmail until full disconnect, migration and security review are complete.

Provider revocation can have an ambiguous outcome: Google may revoke a token but the response or local confirmation may be lost. Keep revocation pending and retain any encrypted token; a subsequent error is not proof of success. An interrupted authorization or token rotation can also leave a grant without a recoverable local token. A pending disconnect with no token does not prove that no grant exists. Until a verified recovery mechanism is available, tell the owner to inspect and, if necessary, revoke RoleRiver's access in their Google account. Do not log token material. These flows remain inactive pending integrated security review.

Interrupted processing decisions can be replayed in bounded pages using `recoverProcessing`. A returned end cursor only ends that traversal; it does not prove that no work was inserted behind it. Callers must repeat sweeps from the beginning and retry failures. No scheduler is wired yet.

The local processing API currently fails closed for retaining or releasing role/evidence holds. A message can support multiple owners; a coordinator must establish and authorize the complete owner set before those operations can be enabled. Existing retained holds cannot yet be released through this API and may keep text indefinitely. Discard is a trusted explicit decision and protects registered holds, but cannot detect unregistered role dependencies. The manual-import path also lacks connection-bound provenance for Gmail-derived or unknown-origin text, so its copies cannot yet be reliably included in disconnect cleanup.
