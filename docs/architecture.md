# Architecture

Status: accepted architecture; implementation is staged in the roadmap. Start with one local TypeScript CLI composition root, functional domain logic and explicit application orchestration. Validate at I/O boundaries; provider-specific types stay in adapters. Do not add services or speculative ports merely to showcase architecture.

The CLI vertical slice reads relevant CV and vacancy text plus optional preferences, checks confirmed objective exclusions, makes one logical AI semantic assessment request, validates structured output and evidence references, applies operational policy, and returns a disposition. Later pipeline: policy-gated sources → sanitize and normalize with provenance → identity/versioning → AI assessment → deterministic policy → notification. Explicit workflows call the provider for semantic assessment; untrusted text cannot issue instructions or invoke tools. Model failures yield controlled errors or unknowns. Use bounded observable retries, timeouts and an injectable clock.

The CLI MVP remains database-free. Later structured operational data uses DynamoDB and private objects use S3, behind narrow domain-oriented repository and object-storage ports. Use ElectroDB with AWS SDK v3 and its DynamoDB Document Client within the persistence adapter to reduce entity and key-modeling boilerplate and improve type safety; direct SDK operations remain available when clearer. Direct calls and in-process events do not guarantee durability. For an actual cross-process boundary, use versioned JSON Schema, CloudEvents-compatible envelopes, producer/consumer validation, compatibility rules, IDs and timestamps; minimize sensitive payloads. OpenAPI and AsyncAPI are introduced when the corresponding boundary exists. Before distribution, specify ordering, idempotency, retries, dead letters, observability and transactional delivery.

Tooling baseline: Node LTS, strict TypeScript/ESM, pnpm workspaces, Zod, Vitest and mise; OpenAI Responses API behind a narrow port with offline mocks. Python with uv, pytest, Ruff and Pyright only when justified. Native development first; containers for relevant infrastructure or isolated workers later. No Nx or initial Turborepo. CI should install from a lockfile and run format, lint, typecheck and tests. The C01 workspace pins Node and pnpm in `mise.toml`, with dependency versions in `package.json` and `pnpm-lock.yaml`; local checks have passed, and the first CLI and provider adapter are implemented. Optional future AWS and Python components are not implemented.

See the [initial persistence design](persistence-design.md) for concrete access patterns and local isolation.

## Persistence and local operation

Design access patterns before selecting single or multiple tables, partition/sort keys and GSIs: tenant-scoped recent vacancies, source/external-ID lookup, candidate assessments, deadline queries and sync state, all paginated without routine unbounded scans. Store metadata, provenance, versions, profiles, assessments, deduplication keys, checkpoints, notification history, users and connection metadata in DynamoDB. Store minimized original content, CVs, permitted attachments and large artifacts in private S3, with references and integrity metadata in DynamoDB; separate private buckets from public static assets. Respect item-size limits. Conditional writes and transactions protect concurrent deduplication and idempotency; define bounded retries and consistency per operation. TTL is asynchronous and does not enforce an exact deadline. DynamoDB and S3 cannot commit atomically together: design retry-safe references, recovery and orphan cleanup; external notifications cannot promise exactly-once delivery.

At the persistence milestone use pinned DynamoDB Local in Docker Compose with the same adapter as AWS and explicit endpoint/credential configuration. Use a filesystem object adapter initially, or justify an S3-compatible emulator, and run shared behavioral contracts; in-memory adapters support fast unit tests. Default development and CI need no live AWS account. Local scheduling and in-process orchestration remain first. Emulator results do not prove AWS IAM, encryption, TTL or deployment behavior: validate those later in explicitly authorized cloud tests. AWS CDK and production resources remain staged, not provisioned.
